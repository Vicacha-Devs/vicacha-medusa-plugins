# Modules

Three custom Medusa modules that make up the B2B data layer.

```
modules/
├── company/    b2b_company   — companies and their employees
├── quote/      b2b_quote     — request-for-quote threads and messages
└── approval/   b2b_approval  — cart approval gates and company-level settings
```

Each module follows the standard Medusa v2 module layout:

```
<module>/
├── index.ts          exports MODULE constant + Module() definition
├── service.ts        extends MedusaService with any custom methods
├── models/           data models (one file per entity)
├── types/            internal create/update type aliases (module-local only)
└── migrations/       generated MikroORM migration files
```

---

## `b2b_company`

**Models:** `Company`, `Employee`

A `Company` has many `Employee` records. Each `Employee` links to a Medusa `Customer` via a remote link (defined in `src/links/employee-customer.ts`). The `spending_limit` field on `Employee` is a BigNumber — set to `0` to mean unlimited.

The `spending_limit_reset_frequency` enum controls how often the employee's spend window resets for the spending-limit check in `completeCartWorkflow`.

**Service token:** `COMPANY_MODULE`

**Custom methods:** none — fully auto-generated by `MedusaService`.

---

## `b2b_quote`

**Models:** `Quote`, `Message`

A `Quote` tracks the lifecycle of a request-for-quote negotiation. The `draft_order_id`, `order_change_id`, and `cart_id` fields are plain string references (not FK columns) — the actual join is handled by virtual links registered in `src/links/quote-links.ts` via `MedusaModule.setCustomLink`.

`Message` belongs to a `Quote` and can be authored by either a customer (`customer_id`) or a Medusa admin user (`admin_id`).

**Service token:** `QUOTE_MODULE`

---

## `b2b_approval`

**Models:** `Approval`, `ApprovalSettings`, `ApprovalStatus`

`ApprovalSettings` is created once per company (linked via `src/links/company-approval-setting.ts`) and controls which approval gates are active.

`Approval` is created once per required approver type when a cart is submitted for approval. `ApprovalStatus` is a denormalized aggregate (one per cart) that the cart-hook validators read to avoid joining through multiple `Approval` rows on every cart mutation.

**Service token:** `APPROVAL_MODULE`

**Custom methods:**
- `hasPendingApprovals(cartId: string): Promise<boolean>` — returns `true` if any `Approval` for the cart is still `pending`.

---

## Generating migrations

After editing a model, regenerate migrations from the plugin root:

```bash
medusa plugin:db:generate
```

Migration files land in `migrations/` and are auto-applied by `medusa db:migrate` in the host application.
